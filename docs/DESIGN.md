# CANログ取得治具 設計仕様 v2.5（2ch同時記録 + RTC）

> ビルド手順・ディレクトリ構成はプロジェクトルートの [`../README.md`](../README.md) を参照。

PCとCANインタフェースを持ち込めない現場で、単独でCANログを取得するための治具。
CAN1(500kbps) / CAN2(250kbps) の**2バスを同時に**SDカードへ記録し、PC側スクリプトでBLFへ変換して解析側へ送る。

部品表・ピンアサイン・基板設計指針は [`HARDWARE.md`](HARDWARE.md)、
プログラムの中身の解説は [`TECHNICAL.md`](TECHNICAL.md)、
現地での操作手順は [`USAGE.md`](USAGE.md) を参照。

```
測定対象 CAN1(500k)                    測定対象 CAN2(250k)
   │                                    │
   ├ RESD1CANY → ISO1042DWV             ├ RESD1CANY → ISO1042DWV
   ├ ESP32内蔵TWAI                      ├ MCP2515 (HSPI)
   │  Listen-Only                       │  Listen-Only
   └──────┬─────────────────────────────┘
          │  rxTaskTwai / rxTaskMcp (core1) : 打刻してリングへ
          │  writerTask (core0) : 時刻順マージ → SDへ
          │
   ESP32-WROOM-32E-N16
          ├ microSD (VSPI) → LOG0001.BIN / LOG0001.TXT(統計)
          ├ MCP7940N (I2C) → 記録開始時刻
          ├ 開始/停止ボタン
          └ 状態LED
```

## 1. 構成の考え方

### 1.1 なぜCH2をMCP2515にするか

ESP32(classic)の内蔵TWAIコントローラは**1chしかない**ため、2バス同時記録には外付けコントローラが必須。
負荷の高い500kbpsを内蔵TWAI、250kbpsをMCP2515に割り当てている。

| | CH1 = 内蔵TWAI | CH2 = MCP2515 |
|---|---|---|
| 受信バッファ | HW FIFO + ドライバキュー128段 | RXB0/RXB1の2段（BUKTロールオーバ有効） |
| ビットレート | 500 kbps | 250 kbps |
| 上限フレームレート | 約4,000 frame/s | 約2,250 frame/s |
| 連続フレームの到着間隔 | 約250 µs | 約444 µs |
| 許容サービス時間（2段） | — | 約888 µs |
| 実測見込みの読み出し時間 | — | 50〜100 µs（INT応答 + SPI 14byte @10MHz） |

CH2は余裕率およそ8倍あり、250kbpsであれば2段バッファでも成立する。
**将来CH2も500kbpsにする場合は許容時間が約500µsまで縮む**ので、その時は再評価が必要。

### 1.2 Listen-Onlyで動かす

両chともACKを返さない完全な受信専用モードで動作するため、バスに一切影響を与えない。
その代わり**ボーレートを間違えてもエラーを出さず「0件で終わる」**。
統計ファイルにCH1/CH2それぞれの受信0件警告を出すようにしている。

## 2. スループット試算

### 2.1 「取得したい信号数1000〜2000」の解釈

これはDBC上の**シグナル数**であり、治具の負荷とは直接関係しない。
治具はDBCを持たず生フレームを丸ごと記録するので、シグナルが何本あっても動作は変わらない。
効くのは**フレームレート [frame/s]** だけ。デコードはPC側の CANalyzer + DBC で行う。

### 2.2 物理上限（設計最悪値）

| チャネル | 条件 | 上限フレームレート |
|---|---|---|
| CH1 | 500 kbps / 8byte | 約3,800〜4,500 frame/s |
| CH2 | 250 kbps / 8byte | 約1,900〜2,250 frame/s |
| 合計 | — | **約6,250 frame/s** |

### 2.3 データ量とSD書き込み速度

| 保存形式 | 1フレーム | 6,250 frame/s | 10分 | 1時間 |
|---|---|---|---|---|
| **バイナリ（既定）** | 24 byte | 約150 kB/s | 約90 MB | 約540 MB |
| ASCテキスト | 約64 byte | 約400 kB/s | 約240 MB | 約1.4 GB |

Arduino-ESP32 標準 `SD`（SPI 20MHz）の実効書き込み速度は概ね300 kB/s〜1 MB/s。
2ch同時記録でASCテキストを選ぶと400 kB/sとなり成立しないカードが出てくるため、
**既定を24byte固定長バイナリにしている**。150 kB/s なら十分な余裕がある。

ASCモードは `pio run -e asc_format` で使える。現地でテキストとして中身を確認したいときのデバッグ用。

### 2.4 バッファ設計

| リング | 段数 | サイズ | 吸収できるSD停止時間 |
|---|---|---|---|
| CH1 | 2048 | 約49 KB | 約0.5秒（4,000 frame/s時） |
| CH2 | 1024 | 約25 KB | 約0.45秒（2,250 frame/s時） |

安価なSDカードは内部GCで数百ms書き込みが止まることがあるため、その吸収が目的。
記録終了時に `ring max used` を統計ファイルへ残すので、実機で余裕を確認したうえで
`config.h` の `RING_SIZE_CH1 / RING_SIZE_CH2` を調整できる。

ESP32-WROOM-32E-N16 のフラッシュは16MBだが**SRAMは520KB**（実使用可能なDRAMは約320KB）。
リングを増やす際はヒープ残量（起動時にシリアルへ出力する）を確認すること。

### 2.5 記録時間の上限

FAT32の1ファイル上限は4GB。バイナリ150 kB/s なら約7.4時間まで1ファイルで記録できる。
「10分程度」の要求に対しては十分だが、それ以上を常用するならファイル自動分割（今後の課題）を入れる。

## 3. 実機測定の結果（2026-08-10 / LOG0002）

測定対象のCH2（250kbps）に接続して6.16秒間記録した結果。

| 項目 | 値 |
|---|---|
| フレーム数 | 4,426（平均 719 frame/s） |
| ID種類数 | 40（標準ID 25 + 拡張ID 15） |
| 周期構成 | 10ms×6種、20ms×3種、100ms×多数、1000ms×多数 |
| `bus err alerts` | 0 |
| リング最大使用 | 12 / 1024 |
| SD書き込み最大 | 4,831 µs |

**実測フレームレート719 frame/s** は設計最悪値（CH2で2,250 frame/s）に対して3割程度。
リングバッファも1024段中12段しか使っておらず、**SD側・バッファ側は大幅に余裕がある**ことが確認できた。

### 3.1 v2.2で発生していた取りこぼしと修正

周期メッセージの欠落を数えたところ、**全体の1.21%（54フレーム）**が失われていた。
特にID 341（20ms周期）は17.3%が欠落。

原因は `mcpIsr()` で `portYIELD_FROM_ISR()` を行っていなかったこと。
`vTaskNotifyGiveFromISR()` の第2引数に `nullptr` を渡していたため、
ISRから抜けるときにタスク切り替えが要求されず、**CH2受信タスクの起床が
次のティック（最大1ms）まで遅れていた**。

測定データがこれを裏付けている。

| 観測 | 内容 |
|---|---|
| 1回の起床で読んだフレーム数 | 1件…1,672回 / **2件…1,311回** / 3件…44回 |
| 起床間隔の最小値 | **999 µs**（1000µs未満は3,026回中わずか9回） |

250kbpsでは8byteフレームが約444µs間隔で到着するため、1ms待つと
MCP2515のRXB0/RXB1がちょうど埋まり、3フレーム目で溢れる。

**v2.3での修正**

1. `mcpIsr()` で `portYIELD_FROM_ISR()` を実行する（起床遅延を1ms → 数十µsへ）
2. `/INT` がLowの間は通知を待たずに読み出しを継続する
   （MCP2515の `/INT` はレベル出力のため、ドレイン中に届いたフレームでは
   新しい立ち下がりエッジが出ず、エッジ検出を取りこぼす経路があった）

### 3.2 v2.3で作り込んだ不具合（v2.4で修正）

v2.3で `/INT` のレベルチェックを追加した際、**「記録中でない」判定をその後ろに置いてしまった**。

```cpp
if (digitalRead(MCP_INT_GPIO) == HIGH) {   // Lowだとここを通らない
  ulTaskNotifyTake(...);
}
if (g_state != ST_LOGGING || !g_mcpReady) continue;   // 待機中はここで戻る
```

**CH2をバスに接続した待機状態**では `/INT` がLowに張り付くため、
どこでもブロックせずにループが回り続ける。このタスクは優先度19でコア1に固定されており、
優先度1の `loopTask`（`setup()` と `loop()` が動く）を完全に飢餓状態にする。

症状は次のとおりで、CH2を接続していない環境では再現しない。

- `setup()` の最後の2行（`free heap after init` / `type HELP ...`）が出力されない
- シリアルコマンドが一切効かない
- 開始/停止ボタンが効かない
- LEDが更新されない（消灯のまま）

**v2.4での修正**: 状態判定を先頭へ移し、記録中でなければ必ず `vTaskDelay()` で眠るようにした。
あわせて、`/INT` がLowのままフレームが読めない異常時の保険として、
1件も読めなかった場合に `vTaskDelay(1)` を入れている。

### 3.3 タイムスタンプ精度について（解析側への申し送り）

ESP32のTWAIもMCP2515も**ハードウェア受信タイムスタンプを持たない**。
本ファームは受信タスクがフレームを取り出した時刻を打刻している。

| 項目 | CH1（内蔵TWAI） | CH2（MCP2515） | PC接続型インタフェース |
|---|---|---|---|
| タイムスタンプ源 | ソフトウェア（esp_timer, 1µs分解能） | 同左（INT応答分の遅れが加わる） | ハードウェア |
| 通常時の誤差 | ±数十µs | ±100µs程度 | ns〜µs |
| バースト時 | キュー滞留分だけ遅れる（最大数ms） | 同左 | 影響なし |
| ch内のフレーム順序 | 保証される | 保証される | 保証される |
| エラーフレーム | **記録不可**（統計カウントのみ） | **記録不可**（同左） | オブジェクトとして記録 |

**ch間の相対時刻は同じesp_timerで打刻しているので比較可能**だが、上記の誤差が乗る。

RTC（MCP7940N）が与えるのは「計測開始が実世界の何時何分か」というアンカーだけで、
フレーム間隔の精度には関与しない。

本治具のログは**シーケンスと中身の解析**用と位置づけ、バス負荷率・フレーム間ギャップ・
エラーフレーム解析が必要な案件はPC接続型のCANインタフェースで取得する、という線引きを
治具の配布前に関係者間で合意しておきたい。

## 4. LED表示と異常時の挙動

| 状態 | LED | 意味 |
|---|---|---|
| 待機 | 消灯 | 電源ON・SD認識済み・MCP2515疎通OK。開始ボタン待ち |
| 記録中 | 200ms周期で点滅 | CANログ取得中。SDを抜かないこと |
| 停止 | 点灯（continuous） | ファイルクローズ完了。**SD取り外し可** |
| 異常 | 80ms周期で高速点滅 | 下表参照。開始ボタンで再試行 |

停止処理（残データの書き出しとファイルクローズ）が終わってから点灯に切り替わるので、
**LEDが点灯したことがSD取り外し可の合図**になる。

記録中に異常が起きた場合も、いきなり高速点滅に移るのではなく
**そこまでのログの書き出し・ファイルクローズ・統計ファイル出力を済ませてから**高速点滅になる（縮退保存）。
そのため異常終了でも `LOG0001.BIN` と `LOG0001.TXT` は残り、統計ファイルの `fault` 行に要因が記録される。

| fault | 意味 |
|---|---|
| `SD card not found / mount failed` | SDカード未挿入または認識不良 |
| `cannot create log file on SD` | 書き込み保護／FAT破損／容量不足 |
| `SD write failed (card full or bad contact)` | 記録中の書き込み失敗。容量または接触を確認 |
| `CH1 TWAI driver init failed` | 内蔵TWAIの初期化失敗（通常は起こらない。要報告） |
| `CH2 MCP2515 not responding` | MCP2515のSPI疎通不良（基板不良・はんだ不良） |
| `CH1 bus off` | CH1がBus Off（Listen-Onlyでは通常起こらない。要報告） |

高速点滅からは**開始ボタンで復帰できる**（内部の後始末をやり直してから記録を開始する）。
復帰しない場合は電源を入れ直す。

なお**RTCの異常では停止しない**。時刻が読めない場合は `unix_time = 0` として記録を続行し、
統計ファイルに注記を残す。

## 5. 操作手順（概要）

1. 治具の電源を入れる（LED消灯＝待機。高速点滅ならSDカードを確認）
2. CH1コネクタを500kbps側、CH2コネクタを250kbps側の取得ポイントへ接続する
3. **開始ボタン**を押す → LEDが点滅を始める
4. 事象を再現させる
5. **停止ボタン**を押す → LEDが点灯に変わるまで待つ
6. LED点灯後にSDカードを抜く（点滅中に抜くとファイルが壊れる）
7. `LOG0001.TXT` を開き、以下を確認する
   - `exit` が `normal (stop button)` であること
   - `start time` が正しいこと（大きくずれていればRTCの電池切れ）
   - CH1 / CH2 それぞれの `frames logged` が0でないこと
   - `ring dropped` / `ctrl missed` / `ctrl ovf events` がすべて0であること
   - `*** WARNING` の行が無いこと（すべて問題なければ `result : OK` が出る）
8. `LOG0001.BIN` と `LOG0001.TXT` を解析側へ送付する

> **`ctrl ovf events` の読み方**
> この値はMCP2515のオーバフロービットを200ms周期でポーリングして検出した**回数**であり、
> 落ちたフレーム数ではない（1回のカウントに複数フレームの欠落が含まれ得る）。
> **0でなければ取りこぼしあり、数は不定**と判断する。
> CH1側の `ctrl missed` はドライバがフレーム数で数えているのでこちらは実数。

## 6. 出力ファイルとBLF変換

### 6.1 LOG0001.BIN（既定）

リトルエンディアン。ヘッダ32byte + 24byte固定長レコード × N。

**ヘッダ 32byte**

| offset | 型 | 内容 |
|---|---|---|
| +0 | char[8] | magic `"CANLOG02"` |
| +8 | uint16 | version = 2 |
| +10 | uint16 | record_size = 24 |
| +12 | uint32 | CH1 ビットレート [bps] |
| +16 | uint32 | CH2 ビットレート [bps]（0ならCH2無効） |
| +20 | uint32 | 計測開始のUNIX時刻（**UTC**）。0ならRTC無効/未設定 |
| +24 | uint64 | t0_us：計測開始時刻（治具のesp_timer基準） |

**レコード 24byte**

| offset | 型 | 内容 |
|---|---|---|
| +0 | uint64 | ts_us：受信時刻（esp_timer基準の絶対値） |
| +8 | uint32 | ID（11bit または 29bit） |
| +12 | uint8 | DLC（0..8） |
| +13 | uint8 | flags：bit0 = 29bit ID / bit1 = リモートフレーム |
| +14 | uint8 | channel：1 = CH1 / 2 = CH2 |
| +15 | uint8 | reserved（0固定） |
| +16 | uint8[8] | データ |

レコードは**チャネル内では時刻順**だが、チャネル間の順序は保証していない
（ファーム側で約5msのマージ窓を持たせているが、保険としてPC側で必ず時刻ソートする）。

### 6.2 BLFへの変換

```bash
pip install python-can
python tools/bin_to_blf.py LOG0001.BIN -o LOG0001.blf
```

RTCが動作していれば `unix_time` が入っているので、**開始時刻の手入力は不要**。
省略時は「ヘッダの `unix_time` → それが0なら入力ファイルの更新時刻」の2段フォールバックになる。
明示指定したい場合のみ `--start "2026-08-09 14:05:00"` を使う。

BLF内のチャネル番号は 1 = CAN1 / 2 = CAN2 になり、CANalyzerの設定とそのまま一致する。

#### タイムゾーンの扱い

治具は `unix_time` に**UTC**を格納する。一方 python-can は BLFヘッダの計測開始時刻
（SYSTEMTIME）へ**UTCをそのまま書き込む**が、**CANalyzer はこのフィールドを
現地時刻として表示する**。そのため補正しないと、CANalyzer 上で9時間前にずれる。

`bin_to_blf.py` は**既定で現地のUTCオフセットを全タイムスタンプに加算**し、
CANalyzer に現地時刻が表示されるようにしている。
全フレームを同じ量だけずらすので、**フレーム間の相対時刻は変わらない**（実データ4,426件で検証済み）。

| オプション | 動作 |
|---|---|
| （既定） | このPCのタイムゾーンで補正。日本なら +9時間 |
| `--tz-offset 9` | 補正量を時間単位で明示指定 |
| `--utc` | 補正せずUTCのまま出力（従来動作） |

治具の記録開始が 15:02:27（JST）の場合の表示。

| モード | CANalyzer の Start |
|---|---|
| 既定 | **2026-09-01 15:02:27** |
| `--utc` | 2026-09-01 06:02:27 |

**動作確認済み**: python-can 4.6.1 にて、C側の構造体（`ring_buffer.h` の `CanRec` / `BinHeader`）で
書き出したバイナリを `bin_to_blf.py` でBLF化し、`can.BLFReader` で読み戻して
標準ID / 29bit ID / リモートフレーム / DLC=0 / 2chの時刻順マージ / RTC時刻の反映
が欠落なく往復することを確認した。ASC経路（`asc_format.h` → `can.logconvert` → BLF）も確認済み。

### 6.3 LOG0001.TXT（統計）

CH1/CH2ごとのフレーム数・取りこぼし数・リング最大使用量、SD書き込み最大所要時間、
記録開始時刻、終了種別（`exit`）と異常要因（`fault`）を記録する。
**ログの信頼性判定はこのファイルで行う。** 読み方は §5 の手順7を参照。

## 7. RTC（MCP7940N）の時刻設定

RTCには**現地時刻（日本時間）**を設定する。ファームウェアがUTCへ変換して保存するため、
PC側で正しい時刻が表示される。

```
pio device monitor
> SETTIME 2026-08-09 14:05:00
[OK] RTC set to 2026-08-09 14:05:00 (local)
```

| コマンド | 内容 |
|---|---|
| `SETTIME YYYY-MM-DD HH:MM:SS` | RTCに現地時刻を設定（記録中は不可） |
| `GETTIME` | 現在のRTC時刻を表示 |
| `TRIM [-127..127]` | 発振周波数の補正値を表示／設定（`HARDWARE.md` §11.6） |
| `STATUS` | 状態・fault・ヒープ残量・**RTC診断フラグ** |
| `HELP` | コマンド一覧 |

`STATUS` はRTCの診断フラグを出す。電源断→復帰テストで失敗したときの切り分けに使う。

```
rtc flags: OSCRUN=1 PWRFAIL=0 VBATEN=1 (RTCWKDAY=0x29)  trim=+0 (+0.0 ppm)
```

| フラグ | 意味 |
|---|---|
| `OSCRUN=0` | 発振していない（`SETTIME` 未実行か水晶の問題） |
| `VBATEN=0` | **バックアップ無効**。電源断で時刻が消える |
| `PWRFAIL=1` | 電源断からの復帰履歴あり（正常な表示） |

タイムゾーンは `config.h` の `RTC_UTC_OFFSET_SEC`（既定 JST = UTC+9）で変更できる。

**製作時に一度設定すれば、CR2032が切れるまで保持される。**
精度は外部水晶次第（温度補償なし）だが、必要なのは秒〜分オーダーなので実用上問題ない。

電池交換後や発振が止まっている場合は `unix_time = 0` として扱われ、記録は続行される。
起動時にシリアルへ警告が出るので、その場合は `SETTIME` で再設定する。

| 起動時メッセージ | 意味 |
|---|---|
| `MCP7940N: 2026-08-09 14:05:00 (local)` | 正常 |
| `oscillator not running. check crystal / load caps.` | **水晶が発振していない**（負荷容量の不整合・実装不良） |
| `time not set. use SETTIME command.` | 時刻未設定 |
| `MCP7940N not responding` | I2C疎通不良 |

## 8. ビルド環境

- **PlatformIO** / `espressif32@6.8.1`（= arduino-esp32 2.0.17）
- ボード: `esp32dev` / Flash Size 16MB
- 追加ライブラリ: **なし**（`SD` / `SPI` / `Wire` はフレームワーク同梱、
  MCP2515・MCP7940Nドライバは自作で同梱）

```bash
pio run                 # ビルド
pio run -t upload       # 書き込み（BOOT+ENを押してダウンロードモードにしてから）
pio device monitor      # シリアルモニタ（115200）
```

### バージョン固定の理由

本ファームは `driver/twai.h` を直接使っており、**arduino-esp32 3.x ではAPI・ヘッダ構成が変わるため
ビルドが通らない**。3.x系はEspressifがPlatformIO公式サポートを終了し pioarduino フォークへ
移行しているため、公式プラットフォームを使う限りこの制約は自然に満たされるが、
再現性のため `platformio.ini` で明示的に固定している。

### 書き込みは手動

CH340EはDTR#を持たないため自動リセットができない。
**BOOTボタンを押しながらENボタンを押して離す → BOOTを離す → 書き込み**。

### ファイル構成

| ファイル | 内容 |
|---|---|
| `platformio.ini` | ビルド設定（プラットフォーム/ボード/env） |
| `src/main.cpp` | 状態機械、CH1/CH2受信タスク、書き込みタスク、縮退保存、シリアルコマンド |
| `src/config.h` | ピン配置・ビットレート・バッファサイズ・保存形式・RTC設定 |
| `src/ring_buffer.h` | 24byte固定長レコード定義とSPSCリングバッファ |
| `src/mcp2515.h` | MCP2515 受信専用ドライバ（Listen-Only、外部ライブラリ不要） |
| `src/mcp7940.h` | MCP7940N 用ドライバ（時刻の読み書きのみ） |
| `src/asc_format.h` | ASC 1行の生成（float未使用。ASCモード時のみ使用） |
| `tools/bin_to_blf.py` | PC側 BIN → BLF 変換。ファイル形式の仕様書も兼ねる |

構成違いは `platformio.ini` の env で切り替える。

| env | 用途 |
|---|---|
| `esp32dev` | 通常構成（既定） |
| `ch1_only` | CH1のみ（MCP2515未実装の試作基板） |
| `no_rtc` | RTC無し（MCP7940N未実装の試作基板） |
| `asc_format` | ASCテキスト保存 |

### Arduino IDE で使う場合

`src/main.cpp` は `.ino` ではないためArduino IDEのスケッチとしては開けない。
使う場合は `main.cpp` を `CanLoggerJig/CanLoggerJig.ino` にリネームし、ヘッダを同じフォルダへ置く。
`#include <Arduino.h>` は既に入れてあり、全関数を呼び出し箇所より前に定義してあるので
プロトタイプ宣言の追加も不要。

## 9. 未決事項

1. **実バスのフレームレート** — CANalyzerで CH1/CH2 それぞれの `Statistics`
   （バス負荷率・frame/s）を実測してもらえれば、リングサイズとSD速度要求を確定できる。
   現状は物理上限（合計6,250 frame/s）で設計している
2. **コネクタの誤挿入** — 相手側（測定対象側）が両chとも B02B-XASK-A のため、
   治具側で形状を分けられない。ケーブルの色分け／シルク印字に加え、
   **統計ファイルで両chとも `frames logged` が0でないことを確認する手順**で検出する。
   CAN_GND端子が無い点は残課題（`HARDWARE.md` §12.3）
3. **CH2も500kbpsになる可能性** — ある場合、MCP2515の2段バッファの余裕率が
   約8倍から約2倍に下がる。事前に分かれば設計を見直す
4. **USBメモリ対応** — ESP32(classic)はUSBホスト機能を持たないためSDカードのみ。
   USBメモリが要件なら ESP32-S3 + USB OTG への変更が必要
